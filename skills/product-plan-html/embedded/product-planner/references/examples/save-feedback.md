# 저장 버튼 피드백 개선 · 완성 명세 예시

> 예시 버전: SF-1 · 가상의 프로필 편집 화면입니다. 아래 현황·결정·문구는 작성 깊이를 보여주기 위한 설정이며 실제 서비스 조사, 사용자 승인 또는 검증 결과가 아닙니다.

[화면과 명세 함께 보기](../../assets/examples/save-feedback.html)

## 목적과 근거

- 예시 요청: “저장 버튼을 눌렀는지 모르겠고, 실패했을 때 다시 입력해야 해요.”
- 예시상 현재 동작: 이름을 편집하고 저장할 수 있으나 처리 중 표시와 실패 시 입력 보존 규칙이 없음.
- 문제 가설: 처리 여부를 알 수 없어 반복 실행하거나 화면을 떠날 수 있음. 실제 빈도와 VOC는 미확인.
- 목표: 처리 중·성공·확정 실패·결과 미확인을 구분하고 다음 행동을 알 수 있게 한다. 중복 제출 차단과 입력 유지 여부는 기능 검수로 판정한다.
- 효과 가설: 상태 이해와 실패 후 복구가 쉬워질 것. 현재 성공률·목표 수치·검증 일정은 미정이며 이 예시로 효과를 입증하지 않는다.

## 대안과 예시상 선택

| 안 | 방향 | 이점 | 한계 |
|---|---|---|---|
| A | 버튼에 처리 중 표시만 추가 | 변경 범위가 작음 | 실패·결과 미확인 후 복구를 설명하기 어려움 |
| B · 예시상 선택 | 버튼의 즉시 반응 + 화면 안의 결과·복구 안내 | 진행과 다음 행동을 함께 설명 | 오류·미확인 상태 명세가 추가로 필요 |

B를 선택했다고 가정한다. 색상·컴포넌트 스타일은 실제 작업에서 기존 디자인 규칙을 따른다.

## 범위

프로필 이름 저장의 피드백, 동일 화면 내 입력 유지, 결과 확인과 재시도. 다른 화면의 버튼 개편·자동 저장·오프라인 저장·새 브라우저 세션까지 초안 보관은 제외한다. 화면을 닫았을 때의 입력 복원은 보장하지 않는다.

화면: S-SAVE. 행위자: 현재 프로필을 편집할 권한이 있는 사용자. 실제 권한 경계·이름 유효성 규칙은 프로젝트의 기존 정책을 적용해야 한다.

## 요구사항·정책·검수 연결

<a id="req-sf-01"></a>
### SF-01 · 저장 시작과 반복 실행

- 조건: 변경된 유효한 입력이 있고 기존 편집 권한이 유지됨.
- 행동: 저장 선택 → 처리 중 상태. 입력과 저장 재실행을 잠시 막고 버튼에 “저장 중”을 표시한다.
- UI 규칙: 포커스가 사라지거나 다른 버튼으로 임의 이동하지 않게 한다. 처리 중 상태를 보조기술에도 전달한다.
- 예시 정책 P-SF-01: 처리 중인 동일 작업을 반복 실행하지 않는다.
- 검수 AC-SF-01: 처리 중 다시 활성화를 시도해도 추가 작업이 시작되지 않으며 현재 입력은 유지된다.

<a id="req-sf-02"></a>
### SF-02 · 성공

- 조건: 저장 성공이 확인됨.
- 결과: 같은 화면에서 “저장했어요.”를 표시하고 편집을 다시 허용한다. 저장된 값을 기준으로 변경 여부를 판단한다.
- 정책 P-SF-02: 결과를 알리기 위해 자동으로 다른 화면으로 이동하지 않는다.
- 검수 AC-SF-02: 성공 후 기존 입력이 보이고, 추가 수정이 없으면 저장을 다시 실행하지 않는다.

<a id="req-sf-03"></a>
### SF-03 · 적용되지 않은 실패가 확인됨

- 조건: 작업이 적용되지 않았다는 결과가 확인됨.
- 결과: 입력을 유지하고 “저장하지 못했어요. 입력한 내용은 그대로예요.”와 “다시 저장”을 제공한다.
- 정책 P-SF-03: 수정 후 재시도도 가능하다. 실패 이유가 확인되지 않았다면 원인을 단정하지 않는다.
- 검수 AC-SF-03: 실패 직전의 입력으로 돌아와 수정·재시도할 수 있고, 재시도에도 처리 중 규칙이 적용된다.

<a id="req-sf-04"></a>
### SF-04 · 결과를 아직 알 수 없음

- 조건: 응답 유실 등으로 적용 여부를 판정할 수 없음. 이를 SF-03의 확정 실패로 취급하지 않는다.
- 결과: “저장 결과를 확인하지 못했어요.”와 “결과 확인”을 표시한다. 확인 전까지 같은 작업의 새 저장과 편집을 보류한다.
- 정책 P-SF-04: 결과 확인은 저장을 다시 실행하는 동작이 아니다. 성공 확인 → SF-02, 미적용 확인 → SF-03, 여전히 미확인 → 현 상태 유지.
- 검수 AC-SF-04: 결과 확인을 해도 저장 작업이 중복 실행되지 않으며, 미확인 상태에서 무조건 재시도를 안내하지 않는다.
- 후속 확인: 현재 제품이 이전 저장의 결과를 구분할 수 있는지 개발 확인이 필요하다. 불가능하면 이 경로의 복구 정책을 다시 합의해야 한다. 새로운 API는 이 예시에서 정하지 않는다.

<a id="req-sf-05"></a>
### SF-05 · 상태 이해와 복귀

- 라벨은 저장·저장 중·다시 저장·결과 확인을 구분한다. 상태를 색상으로만 전달하지 않는다.
- 키보드로 입력·저장·복구를 사용할 수 있어야 한다. 상태가 바뀌어도 입력과 버튼의 읽는 순서는 유지한다.
- 제품 화면의 뒤로가기는 기존 경로를 따른다. 처리 중 화면을 떠나는 행위는 저장 취소를 의미하지 않는다. 재진입하면 저장된 값과 남아 있는 작업의 결과를 확인한다. 미완료 작업의 결과가 불명확하면 SF-04를 적용하고, 결과를 확정한 뒤 편집을 허용한다.
- 검수 AC-SF-05: 키보드 사용과 상태 안내를 실제 대상 환경에서 확인한다. HTML 예시 통과만으로 제품 접근성·재진입 동작을 통과 처리하지 않는다.

## 상태표

| 현재 상태 | 사건 | 다음 상태 | 가능한 행동 |
|---|---|---|---|
| 편집 가능 | 유효한 변경 저장 | 처리 중 | 추가 실행 불가 |
| 처리 중 | 성공 확인 | 저장 완료 | 새 편집 |
| 처리 중 | 미적용 실패 확인 | 실패 | 편집·다시 저장 |
| 처리 중 | 결과 불명 | 미확인 | 결과 확인 |
| 미확인 | 결과 확인: 성공/미적용/미확인 | 완료/실패/미확인 | 확인된 상태에 따라 결정 |

결제·동시 편집 충돌·관리자 처리는 이 예시의 대상이 아니다. 실제 관련성이 발견되면 별도 조건으로 추가한다.

## 기법 적용과 검증 계획

SMART로 “알기 쉽게 개선”을 점검한 결과, 기능 완료 조건은 위 검수로 구체화할 수 있지만 효과 목표·기한은 아직 부족하다. 수치를 임의로 넣지 않고 사용자 과제에서 상태 설명 정확성, 중복 실행 시도, 실패 후 복구 여부를 관찰하도록 제안한다.

이 예시는 가상의 UX 명세이므로 실제 사용자 조사·제품 구현·사용성 검증은 미수행이다. 정식 PRD·이슈는 생성하지 않는다. SF-04의 결과 확인 가능 여부는 해당 경로의 인계 전 확인 항목이다.
