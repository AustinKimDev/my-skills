# Evidence rules

Apply these before stating a code fact. Each comes from a real wrong claim.

- **A file is not a screen.** Open it. A route file may only redirect elsewhere.
- **"없다" needs a search of every path.** Absence in one module is not absence. Search all server modules and name the search scope in the claim. Prefer "전체 목록이 없다, 있는 것은 A, B, C" over "목록이 없다".
- **A claim must agree with the rest of the document.** If an option offers to keep "lists A and B only", a fact cannot say no list exists.
- **Grade evidence.** Observed means the file and line were read. Mark inferred and guess as such. A row in an inventory is not code evidence.
- **Sample the inventory.** Check a random sample of rows against code and state the sample size. Do not claim nothing is missing from a name match.
- **Re-read after an edit.** When a follow-up edit adds detail to a fact, verify that detail too.
- **Unknown stays unknown.** List what was not checked: usage, legal duties, production state.

## Before a proposal becomes a decision

Each comes from a proposal a review had to overturn.

- **Find who already reads the column.** Before a plan starts writing to an existing column or status, search its readers. A scheduled job may start penalizing every account.
- **Check other read paths.** A new masking or permission rule must cover every route that returns the field, not only the screen being changed.
- **Do not promise the past.** A new log starts when it ships. Say so instead of promising history it cannot have.
- **Compare with what is already published.** Read the product's terms, policy pages and the app stores' rules against each decision. A policy that promises a second reviewer cannot stand with one operator.
- **Count the operators in every promise.** A rule that needs two people fails with one, however good it reads.
- **Name the entrances.** Push and email entries are functions. Give them rows, and keep the links already sent working.
