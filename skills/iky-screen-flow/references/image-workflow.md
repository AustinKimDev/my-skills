# Image mockup workflow

Use this reference when the task includes new screen images or raster revisions. Catalog-only work with existing assets does not require image generation.

1. Establish the current visual direction, functional screen inventory, shared style specification, and exact copy before starting generation. A small representative set can resolve composition before producing the full catalog; preserve an already selected direction instead of reopening it.
2. Use the [bundled image-generation guide](../embedded/image-generation/GUIDE.md) with the available image tool to create one readable raster screen image per meaningful screen/state. Do not substitute code-rendered HTML/CSS, SVG, canvas, or screenshots of those renderers unless the user explicitly selects that method. Use a consistent target viewport and clear content hierarchy. Do not generate a collage and crop it into purportedly independent screens. Avoid decorative device frames unless the user requests them.
   - Run independent image-generation calls in parallel, one call per screen, using bounded concurrency supported by the current harness. A shared style anchor may be generated and inspected first; dependent revisions follow their inspected originals. Do not serialize every independent screen by habit.
   - Use built-in image generation by default when available. “Parallel” or “batch” does not select a CLI/API backend. Parallel tool jobs do not imply permission to spawn subagents; follow session rules for delegation.
3. When editing, inspect the exact image first and provide it as the reference to the available image-generation/edit tool. State the bounded change and what must remain recognizable. Follow the installed tool/skill's reference-image and output rules. Do not assume a fixed provider, batch CLI, model, or a future asynchronous job result exists.
4. A useful prompt includes the screen's purpose, visible content and actions, current state, Korean copy, viewport, approved visual anchors, and explicit exclusions relevant to that screen. Keep project policies in the project; a source project's six tabs, no-gradient preference, or marketplace rules are not universal.
5. Save the selected generated result into the artifact. Preserve the original selected file byte-for-byte where practical. Record screen ID, relative output path, actual generation source identifier, prompt, reference identifiers, and concise review notes. Keep private local source paths in project-local provenance only, never in a distributable skill.
6. Inspect every new or edited image. Check copy legibility, navigation consistency, control spacing, image proportions, meaningful selected/disabled/error states, and the required exit path. OCR can help find stale terms across many images; it is supporting evidence, not a substitute for visual inspection.
7. Correct demonstrated material failures with targeted image-tool edits. Keep unresolved limitations visible and do not silently count pending/failed generation as a completed screen. Preserve the selected production method throughout revisions, and distinguish generated assets from pre-existing screenshots in provenance.

Illustrative names, counts, prices, and dates must remain labeled as examples. A drawn login button or payment confirmation is a design proposal, not proof that OAuth or money movement works. Reuse unchanged assets and report bounded changes proportionately.

## Provenance of this reusable viewer

The HTML/CSS/JavaScript viewer was extracted from a user-owned iky-screen-flow review artifact in September 2026. It preserves the sectioned full-screen gallery, single SVG map, image preview, search, and connection navigation. Product-specific images, catalogs, prompts, identities, decisions, local URLs, and the historical migration builder are intentionally not bundled. The replacement builder operates on the generic catalog contract.
