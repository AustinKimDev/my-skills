# 예약 취소 정책 변경 · 완성 명세 예시

> 예시 버전: RC-1 · 가상의 무료 회의실 예약 서비스입니다. 정책·현황·사례상 선택은 설명을 위한 설정이며 실제 서비스 규칙, 운영 권한 또는 사용자 승인이 아닙니다.

[사용자·운영 화면과 명세 함께 보기](../../assets/examples/reservation-cancellation.html)

## 문제·대안·선택

예시상 현재는 예약자가 운영자에게 취소를 요청하고 운영자가 처리한다. 직접 취소를 제공하면 대기와 운영 부담을 줄일 수 있다는 가설이 있다. 실제 요청량·처리 시간·운영 비용은 미확인이다.

| 안 | 효과 가설 | 부담과 제약 |
|---|---|---|
| A · 예시상 선택 | 시작 전 본인 예약을 직접 취소 | 시간 경계·중복·결과 미확인 처리 필요 |
| B | 취소 요청만 접수하고 운영자가 승인 | 예외 조정은 유연하나 운영 대기와 처리 부담 유지 |

예시상 A를 선택했다. 조건부 취소 기능의 작동 여부는 검수 가능하지만 운영 부담 감소는 별도 측정해야 한다. 무료 예약이므로 결제·환불은 범위에 없다.

## 범위와 용어

- 대상: 예약자와 이미 관리 권한을 가진 운영자. 새 역할이나 권한을 만들지 않는다.
- 도메인 상태: 예약됨, 취소됨. ‘시작 전/시작 시각 이후’는 이용 가능 여부를 판단하는 조건이다.
- UI 상태: 확인 대기, 처리 중, 확정 실패, 결과 미확인. UI 상태와 예약 상태를 혼합하지 않는다.
- 정책 경계: 서비스가 최종 취소 처리를 판단하는 시각이 시작 시각보다 이른 경우만 허용한다. 정확히 시작 시각이면 허용하지 않는다. 클라이언트 표시만으로 최종 판정하지 않는다.
- 관련 화면: S-LIST 예약 목록, S-DETAIL 예약 상세, S-CONFIRM 취소 확인, S-ADMIN 운영자 예약 조회.
- 제외: 유료 예약·환불, 시작 후 예외 취소, 자동 알림, 취소 되돌리기, 신규 운영자 권한.

## 조건표

| 사례 | 행위자·조건 | 사건 | 결과·복구 | 연결 |
|---|---|---|---|---|
| C-01 | 본인·예약됨·시작 전 | 취소 확정 | 취소됨으로 변경, 목록과 상세에 반영 | RC-01·02·03 |
| C-02 | 본인·예약됨·정확히 시작 시각 또는 이후 | 취소 시도 | 거절, 예약 상태 유지, 시작 이후 불가 안내 | RC-01·04 |
| C-03 | 다른 예약자 | 접근 또는 직접 취소 시도 | 기존 접근 권한에 따라 차단, 예약 정보 유출 금지 | RC-01 |
| C-04 | 본인·이미 취소됨 | 이전 화면에서 재시도 | 취소됨 상태 표시, 취소 부수효과 반복 없음 | RC-03·05 |
| C-05 | 본인·시작 전 화면을 열었으나 처리 시 시작됨 | 취소 확정 | 최종 판정에서 거절, 예약됨 유지 | RC-04 |
| C-06 | 본인·처리 중 | 연속 선택 | 추가 작업 시작 안 함 | RC-02 |
| C-07 | 본인·미적용 실패 확인 | 재시도 | 입력 맥락 보존, 조건 재평가 후 취소 가능 | RC-05 |
| C-08 | 본인·결과 미확인 | 결과 확인 | 재취소하지 않고 현재 예약 상태 확인 | RC-05 |
| C-09 | 운영자·기존 관리 권한 | 예약 조회 | 같은 예약 상태를 확인, 시작 후 새 예외 처리 권한 없음 | RC-06 |

<a id="req-rc-01"></a>
### RC-01 · 자격과 노출

- 정책 P-RC-01: 예약자는 본인 예약에 한해 시작 전에 직접 취소할 수 있다. 정확히 시작 시각부터는 불가하다.
- S-DETAIL에는 예약명·시작 시각·현재 상태와 취소 가능 여부를 함께 표시한다. 취소 불가 시 “예약 시작 후에는 취소할 수 없어요.”를 제공한다.
- 검수 AC-RC-01: 시작 전·정확히 시작·시작 후를 구분해 확인한다. 버튼 숨김 여부만으로 권한 차단을 검증하지 않는다.

<a id="req-rc-02"></a>
### RC-02 · 취소 확인과 처리 중

- S-CONFIRM은 대상 예약, 취소 결과, “예약 유지”와 “예약 취소”를 제공한다. 확정 전 복귀는 예약 상태를 바꾸지 않는다.
- 확정하면 처리 중 표시와 반복 실행 차단을 적용한다. 이 예시에서는 확인 화면 안의 동작을 잠시 막는다. 브라우저·앱 자체를 닫는 행위까지 막는다고 약속하지 않는다.
- 정책 P-RC-02: 화면을 닫았다고 진행 중 취소가 철회되지는 않는다. 재진입 시 예약 상태부터 확인한다.
- 검수 AC-RC-02: 확인 전 예약 유지로 상세에 복귀 가능. 처리 중 추가 취소가 시작되지 않음. 재진입 경로는 실제 제품에서 별도로 확인.

<a id="req-rc-03"></a>
### RC-03 · 완료와 연결 화면

- 성공이 확인되면 “예약을 취소했어요.”와 취소됨 상태를 표시한다. 예약 목록으로 돌아가도 취소됨으로 보인다.
- 정책 P-RC-03: 취소는 되돌리지 않는다. 이미 취소된 예약을 재취소해도 중복 부수효과가 생기지 않아야 한다.
- 검수 AC-RC-03: S-DETAIL·S-LIST·S-ADMIN의 동일 예약 상태가 일치하며, 오래된 화면 재시도는 취소됨으로 정리된다.

<a id="req-rc-04"></a>
### RC-04 · 시간 경계와 경쟁 상황

- 취소 확정 시점의 최종 조건을 다시 판정한다. 상세를 시작 전에 열었다는 이유로 시작 이후 취소를 허용하지 않는다.
- 거절 시 예약 상태를 유지하고 원인을 안내한다. 다시 취소 버튼을 제공하지 않는다.
- 검수 AC-RC-04: C-02·C-05에서 예약됨이 유지된다. 서비스 시각의 기준과 표시 시간대는 실제 프로젝트 규칙 확인이 필요하다.

<a id="req-rc-05"></a>
### RC-05 · 실패·미확인·재시도

- 미적용 실패가 확인되면 “취소하지 못했어요. 예약은 유지돼요.”와 재시도를 제공한다. 재시도는 현재 자격을 다시 평가한다.
- 결과 미확인이면 “취소 결과를 확인하지 못했어요.”와 결과 확인을 제공한다. 미확인이라는 이유로 예약 유지 또는 취소 완료라고 단정하지 않는다.
- 결과 확인으로 취소됨 확인 → RC-03, 예약됨 확인 → 현재 시간 조건에 맞는 화면, 여전히 미확인 → 현 안내 유지.
- 검수 AC-RC-05: 결과 확인은 새 취소를 실행하지 않는다. 반복 활성화·결과 미확인 지속·시간 경계 경과도 확인한다.

<a id="req-rc-06"></a>
### RC-06 · 운영 영향

- 기존 관리 권한을 가진 운영자는 같은 예약 상태를 조회한다. 이 변경은 시작 후 강제 취소 권한을 부여하지 않는다.
- 운영자가 미확인 문의를 받으면 확인 가능한 예약 상태를 기준으로 안내한다. 조회할 수 없다면 해결됐다고 말하지 않는다. 새 지원 채널·응답 시간은 약속하지 않는다.
- 검수 AC-RC-06: 운영자 조회와 사용자 목록·상세가 동일 예약 상태를 설명한다. 갱신 지연이 있다면 확인 시각을 구분하고 실제 허용 지연을 추가 합의한다.

## 상태 전이와 불변 조건

| 도메인 상태 | 사건·조건 | 다음 상태 | 설명 |
|---|---|---|---|
| 예약됨 | 자격 충족·시작 전 취소 성공 | 취소됨 | 목록·상세·운영 조회에 반영 |
| 예약됨 | 시간·권한 거절 또는 미적용 실패 | 예약됨 | 거절 이유와 가능한 다음 행동 안내 |
| 취소됨 | 중복 취소 | 취소됨 | 부수효과 반복 없음 |
| 미확인 UI | 현재 상태 조회 | 확인된 도메인 상태 또는 미확인 유지 | 조회는 상태를 바꾸지 않음 |

불변 조건: 다른 사람의 예약을 취소할 수 없음; 시작 시각 이후 직접 취소 불가; 취소됨을 예약됨으로 되돌리지 않음; 미확인 UI를 확정 도메인 상태로 오인하지 않음.

## 영향·검증·인계 조건

| 결정이 달라질 때 | 함께 확인할 자료 |
|---|---|
| 취소 가능 시간 | C-01·02·05, RC-01·04, 상세·확인 화면, 경계 검수 |
| 취소 되돌리기 허용 | RC-03, 상태 전이, 목록·운영 처리, 제외 범위 |
| 미확인 복구 방식 | RC-05, 결과 확인 화면, 재진입 경로 |

기획 기준으로 정상·취소 전 복귀·실패·결과 미확인·목록 복귀를 명시했다. 실제 정책 승인·제품 구현·실사용 효과 검증은 미수행이다.

이 예시의 인계 전 확인 항목: 실제 서비스의 시간 기준, 결과 확인 수단과 최종성, 운영 화면의 갱신 특성. 모듈 구조·API·테스트 대상 선택·정식 PRD·이슈 분할은 후속 작업이다.
