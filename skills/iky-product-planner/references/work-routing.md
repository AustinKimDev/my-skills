# Work Routing

Infer the work from the request. If ambiguous, offer relevant starting points, not the complete catalog. Work types may be combined or revisited. Do not require an upstream document merely to start a focused improvement.

| Work | Output emphasis |
|---|---|
| Clarify an idea | Problem, audience, evidence, goals, hypotheses, concise one-pager |
| Plan a feature | Planning specification, stories/scenarios, policies, flows, relevant screens |
| Improve an existing screen or feature | Observed baseline, problem, before/after, changed behavior, impact, acceptance |
| Design or revise policy | Conditions, permissions, states, exceptions, operational handling |
| Improve component UX | Action semantics, state/feedback/recovery contract, contextual impact; involve UI expertise when useful |
| Reconstruct current planning | Observed behavior, supporting sources, inferred intent explicitly labeled, documentation discrepancies |
| Research users or competitors | Source-backed findings, comparison, limitations, applicable hypotheses |
| Restructure a service journey | Information architecture, connected flows, entry, completion, cancellation, failure, return |
| Prioritize or define a release | Decision criteria, proposed order, MVP and exclusions, conceptual dependencies |
| Plan operations/admin | Staff workflow, roles, permissions, exceptions, administrative screens |
| Review a plan | Findings, evidence, impact, corrections and decisions needed |
| Verify implementation | Expected versus observed behavior, evidence, untested cases |
| Evaluate outcomes | Metric definitions, measurement plan or available-data analysis, next hypotheses |

Release prioritization is product scope work, not implementation ticket slicing. Planning reconstruction can itself be the requested outcome; do not force a redesign afterward.

Examples: “마이페이지 개선” starts with the affected screen and journey. “저장 버튼 피드백 검토” can remain a bounded UX review. “현재 환불 규칙 문서화” starts from evidence and policy, without generating wireframes.
