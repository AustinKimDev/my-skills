# Artifacts and Storage

## Choose proportional outputs

Use Markdown as the planning authority. Screen work normally adds an HTML low-fidelity review; small changes may use ASCII, and decisions requiring manipulation may add a local prototype. Policy-only work can remain Markdown. Do not produce an entire PRD-shaped package for a small change.

Adapt [planning-review.html](../assets/planning-review.html) for a screen review. It is an intentionally empty structural template, not a finished deliverable. Replace its empty containers with task-specific content and remove irrelevant sections before delivery. Keep actual product implementation separate from planning-preview code.

When calibrating output depth, inspect one relevant finished example: [save feedback](../assets/examples/save-feedback.html) with its [specification](examples/save-feedback.md), or [reservation cancellation](../assets/examples/reservation-cancellation.html) with its [specification](examples/reservation-cancellation.md). They demonstrate alternatives, numbered screen annotations, requirement/policy/acceptance links, state coverage and explicit evidence limits. All product facts and interactions in them are fictional local demonstrations. Do not copy their policies into a real project or load both examples on every task.

Use ordinary links, native buttons and readable static content before adding scripting. A reviewer must be able to reach the named requirement from a screen annotation and return to the specimen. An optional demo should expose relevant alternative outcomes through clearly separated review controls; product controls must show product behavior. Keep the specification revision visible so the relationship can be checked.

The review connects summary, accepted/proposed status, alternatives when needed, screen frames, behavior/policy annotations, relevant states and unresolved/acceptance items. Use stable references back to Markdown. After selection, make the current direction obvious and preserve useful prior comparisons. Do not place new policies solely in HTML.

Use existing project design settings for applicable presentation conventions. Keep the planning workbench visually subordinate to low-fidelity specimens. Detailed UI exploration goes through integrations.md, not an invented planning design system. Prototype actions are local simulations clearly labeled in Korean; never connect payments, messages or writes to live systems by default.

## Save and update

Prefer the established project planning location. If none exists, use docs/planning/<topic>/ with spec.md and review.html as needed. For work without a project, use ~/Documents/product-planner/<topic>/ unless the user chooses another location; announce this fallback. These are storage defaults, not mandatory migrations.

Save meaningful drafts without a repetitive save-confirmation step. Preserve user edits; update existing authorities rather than generating dated duplicates every turn. Keep draft/accepted/open status explicit. Link existing design rules; do not duplicate their tokens or policy ledgers.

## Check before delivery

Check local links, screen/requirement references and agreement between Markdown and HTML. Open the actual review through the session's required browser route; inspect relevant sizes, content overflow, labels and any prototype paths. Resolve the current session's owning workspace before operating Orca tabs. If browsing cannot be performed, report visual verification as unverified rather than claiming completion of it. Follow local server/port guidance when a server is needed.

Provide reopenable artifact links and concise outstanding decisions. PDF export is optional only when requested and uses the available document workflow. Do not install dependencies merely to export a planning artifact.
