# Integration Boundaries

## ui-design

Keep product-planner primary for planning tasks. Load the installed ui-design skill only when its expertise is needed, with a bounded review/exploration brief. Resolve it from the active skill catalog rather than hard-coding an installation path. Do not install a missing skill automatically; state the limitation and continue independent planning.

Forward user goal, relevant evidence, accepted requirements/policies, target screens/components/environment, existing design authority, prior selections, acceptance conditions and unresolved UI decisions. Reuse existing answers. Specify whether the request is review or exploration and that production implementation is outside the planning-support scope. If a limited comparison is sufficient, state the requested option count explicitly.

UI design owns detailed visual/interaction/accessibility decisions and their target-runtime verification. Product planning owns business/user goals, permissions, policies, scope, effectiveness and planning acceptance. Feed UI findings back into planning; a new policy question returns to user decision. Link the authoritative design record rather than copying tokens or maintaining conflicting briefs.

## to-prd and to-issues

Stop before these workflows. Do not run tracker setup, register Linear/GitHub issues, publish a formal PRD, slice implementation tickets, choose implementation modules, or decide module test coverage on their behalf.

Prepare existing context so the next skill need not repeat planning discovery: problem, solution rationale, audience/stories, requirements, policies/states, flows/screens, scope/exclusions, acceptance, known constraints, evidence, decisions and unresolved questions.

The user may next invoke to-prd to synthesize/publish the formal PRD and resolve engineering decisions, or to-issues to break a sufficiently concrete plan/specification into executable slices. Do not enforce a universal sequence or automatically invoke either skill. Product priorities and conceptual dependencies may be documented without drafting implementation tickets.
