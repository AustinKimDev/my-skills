# Chat and conversation

Inbox, conversation, AI, support, channels, and threads are optional examples in [catalog.json](catalog.json). Combine conversation with documents, tools, artifacts, or other task surfaces when useful; no predefined type is required. Messaging, support, and AI chat share an input field but serve different tasks. Establish recipients, response source, real-time expectations, history, attachments, and access requirements.

## Connections and comparisons

Examples: inbox → conversation → thread; service.history → support → service.result; dashboard.workflow → channels → thread. Carry originating context. Link AI evidence to actual source screens and distinguish tool results from explanation.

Compare composers, message groups, tool-progress displays, attachments, and new-message controls in component mode. Use identical long replies/code/numbers/mixed-script text for typography. Layout may compare conversation-only, conversation plus evidence, or inbox plus conversation. Prototype meaningful sending, retry, streaming cancellation, and history-reading paths. Apply the shared five-alternative policy for new design comparisons.

## Specific checks

- Do not force-scroll readers away from older messages. Follow incoming content only when already at the latest position.
- Enter during Korean IME composition must not send. Make newline/send behavior clear.
- Keep the composer and actions usable with mobile keyboards, safe areas, and attachment previews.
- Preserve failed text and attachments, prevent duplicate sending, and expose retry status.
- Distinguish AI streaming, cancellation, errors, citations, and tool progress. Never mark unexecuted tools complete.
- Do not invent read/online/waiting states as real facts. Label prototype simulations.

Use better-accessibility for input/focus, better-writing for messages, better-typography for text density, and better-ui for purposeful motion.
